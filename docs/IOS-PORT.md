# Lewd Vault on iOS: research and feasibility

This is the research behind an iOS port. It answers what is possible, what breaks, and what a
build-and-sign pipeline looks like. It does not contain code changes yet. It is written to be read
next to `docs/GUIDE.md` (what the app does today) and `docs/PLAN.md` (how earlier rounds were run).

The goal, as asked: a **sideloaded IPA**, not an App Store release. Build it, sign it, install it
on a device the user controls (AltStore / SideStore / TrollStore / a free or paid Apple developer
account).

The short version: **the port is feasible, but it is a real port, not a rebuild of the same
binary.** Tauri 2 has a working iOS target, and the shared page in `ui/` already runs in a WebKit
webview. The hard parts are (1) how media is served (a custom scheme behaves differently on iOS),
(2) the Windows-only paths in the Rust backend (`explorer`, `trash`, `%LOCALAPPDATA%`, the global
shortcut), and (3) the build/sign toolchain, which needs macOS plus a small restructuring of the
Rust crate. None of those are blockers; each has a known fix.

**Two things outrank the rest, per the user's priorities:**

1. **Format compatibility.** The iOS app must read and write the *same vault folder* as the Windows
   app — same `index.csv`/`views.csv`, `_app/` layout, file names, ids and encryption — so a folder
   round-trips between the two with no loss. That contract is spelled out in
   `docs/IOS-PHASE-1.md`; every later decision has to respect it.
2. **Liquid Glass.** The iOS app should look native, not like a Windows app in a phone frame.
   Liquid Glass (iOS 26) has no free adoption in a webview, but WebKit exposes the real system
   material as `-apple-visual-effect: -apple-system-glass-material` (gated on
   `HAVE_MATERIAL_HOSTING`, which is defined for `PLATFORM(IOS)`), with `backdrop-filter` as the
   portable fallback. Details and the design tokens are in `docs/IOS-PHASE-1.md`.

## 2. Tauri 2 on iOS: what the toolchain gives you

Tauri 2 supports iOS (`tauri ios init|dev|build|run`). The moving parts:

- **Webview**: WKWebView, via `wry`. Custom protocols are registered as `WKURLSchemeHandler`s
  (`wry/src/wkwebview/mod.rs` calls `config.setURLSchemeHandler_forURLScheme`).
- **Minimum iOS version**: `bundle.iOS.minimumSystemVersion` in `tauri.conf.json`, **default 15.0**
  (per the config schema). 15.0 is a safe floor; the JS features the app uses need 15.4+
  (`crypto.randomUUID`) and some need far newer (section 3).
- **Xcode project**: generated by **XcodeGen** from a `project.yml` template
  (`crates/tauri-cli/templates/mobile/ios/project.yml`). You can supply your own template with
  `bundle.iOS.template`, and extra frameworks with `bundle.iOS.frameworks`.
- **Info.plist**: Tauri looks for `Info.plist` / `Info.ios.plist` next to `tauri.conf.json`, and
  `bundle.iOS.infoPlist` can point at a file to merge. This is where ATS and background settings go.
- **Build host**: iOS builds **require macOS + Xcode**. `tauri ios init` shells out to XcodeGen and
  Xcode's build tools; it does not run on Windows or Linux. That means a macOS CI runner (GitHub
  Actions `macos-latest`) or a Mac.
- **IPA output**: `tauri ios build` archives and exports an IPA. Flags that matter here:
  `--no-sign` (skip signing, produce an unsigned archive/IPA), `--archive-only`, and
  `--export-method` = `app-store-connect | release-testing | debugging`. `create_ipa()` zips
  `Payload/` with deflate.
- **Signing**: either an Apple API key (`APPLE_API_KEY`, `APPLE_API_KEY_PATH`,
  `APPLE_API_ISSUER`) or a `DEVELOPMENT_TEAM` in config, with `allow_provisioning_updates`.

**Conclusion:** the iOS target is a supported, first-class path. The work is in the app, not the
build system.

## 3. The origin and media problem (the biggest one)

### 3.1 The app hardcodes the Windows origin

Tauri serves custom protocols from a different origin per platform
(`crates/tauri/src/protocol/mod.rs`):

```rust
if cfg!(windows) || cfg!(target_os = "android") {
    format!("{http}://{scheme}.localhost")   // http://vault.localhost
} else {
    format!("{scheme}://localhost")          // vault://localhost   (iOS/macOS/Linux)
}
```

The frontend assumes the Windows form. `sync-ui.mjs` injects:

```js
const vaultUrl = id => 'http://vault.localhost/' + encodeURIComponent(id);
```

and the Rust side emits the same string in `getThumb` and in the item list (`main.rs`, around the
`http://vault.localhost/` format calls). So on iOS every `vaultUrl(...)` is wrong: the scheme
`http` with host `vault.localhost` is not a registered scheme handler, and there is no such host.

**Fix (small):** make the origin a single value computed once and reused. `window.__TAURI__` exposes
what is needed, or the backend can hand the page the right base URL through the existing `api(...)`
bridge. The same string must be used for `getThumb`, the item list, `localFetch`, and the media
`<video>`/`<audio>`/`<img>` sources.

### 3.2 Why the custom scheme is the wrong tool for media on iOS

This is the part that decides the architecture. On iOS, WebKit routes `<video>`/`<audio>` through
AVFoundation, which is picky about custom URL schemes:

- **WebKit bug 146351** (`[GStreamer] Audio/video sources do not load via custom URI scheme`) — the
  media loader never reaches a custom scheme handler; the file simply does not play.
- **WebKit bug 324711 / PR 74641** (`[iOS] Custom URL scheme timeouts lead to crashes in
  mediaplaybackd`, reported 2026-09, fixed in WebKit 322083) — WebKit sets
  `AVAssetResourceLoadingContentInformationRequest.isEntireLengthAvailableOnDemand` for custom
  schemes, and expects requests to be answered *immediately*. A request that behaves like a network
  load and times out used to **crash `mediaplaybackd`**; the fix changes that to a load *error*
  instead of a crash. Apple's own note in the patch says some clients "re-implement HTTP loading via
  a custom URL scheme" — and that is exactly what this app's `vault://` does (byte ranges, `206`,
  `Content-Range`). So even on a fixed WebKit, custom-scheme media that looks like a network load is
  a fragile fit, and on devices running older iOS it can crash the media daemon outright.
- A well-known related limit: a custom scheme that answers range requests with a spec-correct
  `200`/`206` and `Content-Length` can still be rejected because AVFoundation insists on the
  "entire length available on demand" contract.

In practice: **images are usually fine over a custom scheme; video and audio are the problem.** The
app is video- and audio-heavy (Library preview clips, the player, Videos, Audio, the coach's clips,
the emergency cover video). So the custom scheme is a risk for a large part of the experience.

### 3.3 The recommended architecture: serve media over loopback HTTP

The app already contains a working loopback HTTP server with the exact semantics media wants:
`fastlane.rs` binds `127.0.0.1:0`, picks a free port, and `serve()` in `main.rs` answers `206` with
`Content-Range` and a 4 MB `RANGE_PIECE`. On iOS, put the media behind a **loopback HTTP server**
(`http://127.0.0.1:<port>/…`) instead of a custom scheme:

- AVFoundation and WebKit treat `http://127.0.0.1` as ordinary HTTP: range requests, seeking and
  streaming all behave normally.
- The page keeps using `fetch`, `<img>`, `<video>` and `<audio>` unchanged — only the base URL
  differs.
- Security: bind to `127.0.0.1` only, require a per-launch random key on every request (the same
  pattern `fastlane.rs` already uses with `x-key`), and check the `Origin` header. Other apps on the
  device cannot reach `127.0.0.1` of another app's sandbox, and nothing off-device can.
- ATS: loopback HTTP to `127.0.0.1` is not blocked by App Transport Security in practice, but the
  safe, explicit move is to add an ATS exception in `Info.plist`
  (`NSAppTransportSecurity` → `NSAllowsLocalNetworking` = true, and/or an `NSExceptionDomains`
  entry for `127.0.0.1` with `NSExceptionAllowsInsecureHTTPLoads`). Confirm on a real device.

There is a ready-made helper for the "serve the app's own assets over localhost" idea:
**`tauri-plugin-localhost`** (iOS supported, per its README). It serves bundled assets on a
localhost port and is worth reading, but it is aimed at the *app's static assets*, not the vault's
media, and it is flagged as carrying real security risk (no auth). For the vault's own media, a
purpose-built loopback server with the `fastlane` key pattern is a better fit. Whichever is chosen,
the media origin must be a plain `http://127.0.0.1:<port>`.

**One-origin alternative:** keep the *page* on the Tauri custom scheme (`vault://localhost` on iOS)
and only put *media* on loopback HTTP. That keeps the IPC bridge and the app's own scripts where
Tauri expects them, and confines the HTTP server to byte-range media. This is the recommended split.

### 3.4 CSP header-size risk

Tauri computes SHA-256 hashes of every bundled script and injects them into the CSP
(`crates/tauri/src/manager/mod.rs`, `set_csp` / `CspHash::Script`). WebKit enforces a **16 KiB limit
on HTTP header size**. With many separate `<script src>` tags (this app injects ~16 of them from
`sync-ui.mjs`) the CSP header can grow large. Mitigations, in order of preference:

1. Set an explicit CSP in `tauri.conf.json` that allows the app's own scripts with `'self'` and
   disables the automatic hash injection via
   `app.security.dangerousDisableAssetCspModification` (the schema documents this). This trades a
   little automatic hardening for a small, fixed header.
2. Bundle the many small scripts into one or two files so fewer hashes are needed.
3. Keep `csp: null` (today's setting) and rely on the fact that the page is served from the app's
   own scheme. Verify the header actually stays under 16 KiB.

This is a "measure it" item: build once and inspect the response header. It is a known Tauri-on-iOS
report, not a certainty.

## 4. Backend work: Windows-only paths and iOS equivalents

| Today (Windows) | Where | iOS approach |
| --- | --- | --- |
| `Command::new("explorer").arg(url)` to open links | `main.rs` `openLink`/`openDownload`, `web.rs` Reddit sign-in | Use the iOS `UIApplication.openURL:` bridge (Tauri's opener plugin, or a small Objective-C/Swift command). `tauri-plugin-opener` supports iOS. |
| `explorer` to reveal a folder (`openDataFolder`) | `main.rs` | No equivalent. Hide the button on iOS. |
| `trash::delete` (Recycle Bin) | `crypt.rs::trash` | `trash` 5.2.9 has **no iOS backend**: its `platform` module is gated to `macos` (not `ios`) and to freedesktop unix; on iOS it will not compile as-is. Options: add an iOS branch that moves files into an app-managed `_trash` folder inside the vault, or gate `trash` out and always use the in-vault trash on iOS. The app already has an in-vault `_trash` concept in Untraceable mode, so reuse it. |
| `%LOCALAPPDATA%\Image Vault` for caches, sources, sign-in | `storage.rs::local_base` | Use the app sandbox: `Application Support` (via `tauri::path`). Caches in `Library/Caches`. |
| Vault next to the `.exe`, or `Documents` | `storage.rs` `exe_dir`/`local_home` | iOS apps cannot write next to themselves. Default the vault to the app's `Documents` (visible in the Files app with the right `Info.plist` keys) and allow "open a folder" through the document picker. Keep the "pick a cloud folder" flow (see below). |
| `attrib +h +s` to hide the Untraceable folder | `storage.rs::hide` | No-op on iOS (already sandboxed). Keep the `#[cfg(windows)]` guard; add a no-op else branch. |
| Global shortcut (`Ctrl+Shift+Space`) | `main.rs` `set_panic_key`, `tauri-plugin-global-shortcut` | The plugin is **not supported on iOS** (per its README). The emergency key must become an in-app control (a button/gesture), or a `UIApplication` shortcut / volume-button gesture if you want it system-wide. Simplest: a prominent in-app panic button plus a shake gesture. |
| `tauri-plugin-single-instance` | `main.rs` | **Not supported on iOS** (per its README). Guard it with `#[cfg(desktop)]`; iOS is single-instance by nature. |
| Self-update (`install_update`) | `maint.rs` | Drop on iOS. Updates come from reinstalling the IPA. Hide Settings → Updates on iOS. |
| Fast lane upload server | `fastlane.rs` | Keep the idea (loopback + key) but note it is for *uploading* large files to the vault. On iOS it still works in principle, but the "slow way" (the Tauri IPC channel) is the fallback. Re-test transfer speed; the WebView2 40 MB/s note does not apply to WKWebView. |
| `image` crate re-encoding, thumbnails | `main.rs`, `dupes.rs` | Pure Rust, builds for iOS. Fine. |
| `rusqlite` | not used | n/a (the app uses CSV + JSON, which is portable). |

Also relevant:

- **`tauri-plugin-dialog` and `tauri-plugin-opener` support iOS** (per their READMEs). Use them for
  file/folder pickers and opening links.
- **`tauri-plugin-fs` supports iOS** if direct FS access from JS is ever needed; today the app goes
  through the Rust `api(...)` bridge, so this may not be needed.
- **`ureq` + `rustls` + `ring`** all build for `aarch64-apple-ios`; `ring` has an
  `aarch64-apple-ios` build path. `getrandom` 0.2 uses `CCRandomGenerateBytes` on iOS (verified in
  its source), so `fastlane`'s random key and `crypt.rs`'s randomness work.
- **The Google Drive flow** (`gdrive.rs`) uses `ureq` and a loopback redirect for the browser
  sign-in. On iOS, `ureq` works, but the browser sign-in redirect and the "open the system browser"
  step need the iOS opener and a URL-scheme or `ASWebAuthenticationSession` redirect rather than
  `explorer`. The Drive-for-desktop folder trick ("point the vault at a synced folder") does **not**
  exist on iOS — there is no user-visible shared folder for Drive/iCloud in the same way. iOS
  replacement: use the app's own sandbox and sync the vault **through the Drive API** (`gdrive.rs`
  already does two-way sync), or use iCloud Drive via a document-based storage provider (bigger
  job). Decide before starting.

## 5. Rust crate restructuring (required)

Tauri mobile needs the app as a **library** that the generated Xcode project links, plus a thin
binary. Today `src-tauri/src/main.rs` is a binary with `fn main()`. The Tauri template uses:

```toml
[lib]
name = "app_lib"
crate-type = ["staticlib", "cdylib", "rlib"]
```

and `src-tauri/src/lib.rs` with:

```rust
#[cfg_attr(mobile, tauri::mobile_entry_point)]
pub fn run() { /* build and run */ }
```

plus a `src-tauri/src/main.rs` that calls `app_lib::run()`. The migration tool
(`crates/tauri-cli/src/migrate/migrations/v1/manifest.rs`) checks for exactly these crate types and
errors if they are missing. So the port includes:

1. Add `[lib] crate-type = ["staticlib", "cdylib", "rlib"]` to `src-tauri/Cargo.toml`.
2. Move the builder setup out of `main()` into `lib.rs::run()`, with `#[cfg_attr(mobile, ...)]`.
3. Keep `main.rs` as a two-line shim.
4. Add `bundle.iOS` config (team, minimum version, frameworks, Info.plist) to `tauri.conf.json`.
5. Add the `bundle.identifier` (already `local.imagevault.desktop`) and iOS icons. iOS needs a
   proper app-icon set (Xcode asset catalog), not the current `icon.ico`/PNG set. `tauri icon` can
   generate the catalog.

`withGlobalTauri: true` is already set, so the page's `window.__TAURI__` usage keeps working.

## 6. Sideloading: how the IPA gets onto a device

Because this is explicitly **not** an App Store release, and the content is NSFW (App Store review
would reject it outright), the install paths are:

| Method | Needs | Notes |
| --- | --- | --- |
| **AltStore / SideStore** | A computer (AltServer) or a local pairing; free or paid Apple ID | Signs the IPA with the user's own certificate, re-signs every 7 days on a free account. The classic sideload route. |
| **TrollStore** | iOS 14.0–16.6.1, 16.7 RC, 17.0 only | Installs IPAs permanently with arbitrary entitlements via a CoreTrust bug. Not available on 16.7.x (non-RC) or 17.0.1+. Best UX *if* the device is in range. |
| **Free Apple ID + Xcode / `ios-deploy`** | A Mac + cable | 7-day provisioning profile, 3 apps max. Good for development. |
| **Paid Apple Developer ($99/yr)** | A Mac or CI | Ad-hoc / development signing with a 1-year profile, up to 100 devices. Cleanest for a personal build. |

For the *unsigned* artifact, `tauri ios build --no-sign` produces an IPA that a signer (AltStore,
TrollStore, or `codesign`/`ldid` in CI) can then sign. For a *signed* IPA, use an Apple API key in
CI with `--export-method debugging` (development) or `release-testing` (ad-hoc).

**Recommended pipeline:** a GitHub Actions job on `macos-latest` that runs `tauri ios build`, with
secrets for either (a) an Apple API key → signed IPA, or (b) nothing → `--no-sign` unsigned IPA that
the user signs locally. `tauri-action` documents the macOS-runner pattern. Build artifacts go to the
release as `LewdVault.ipa`.

Caveat: a **free** Apple ID cannot be automated in CI the same way; AltStore's re-signing is the
practical free path. A paid account is the low-friction path.

## 7. Frontend: touch, keyboard, and web-platform gaps

The page was written for a desktop mouse/keyboard and a Windows webview. On iOS:

- **Touch vs. mouse.** There are ~34 `requestFullscreen`/context-menu/touch handler sites. Check
  every hover-only affordance (tiles, tag suggestions, the sidebar). `contextmenu` for right-click
  menus has no iOS equivalent; long-press is the pattern.
- **Fullscreen.** `Element.requestFullscreen` is not supported in iOS Safari/WKWebView for arbitrary
  elements (only `<video>` via `webkitEnterFullscreen`). The slideshow's "true full screen" and the
  panic-mode full screen must be re-thought (CSS full-bleed within the webview, or
  `video.webkitEnterFullscreen()`).
- **Dialogs.** ~16 `confirm`/`alert`/`prompt` calls across `ui/*.js`. These work in WKWebView but
  look like system alerts and block the UI; the app already has a `toast` and could move these to
  in-page modals for a native feel.
- **Keyboard shortcuts.** The player and Library use keyboard handlers; they are harmless on iOS but
  the app needs on-screen equivalents (the player already has controls).
- **Autoplay.** iOS blocks autoplay of unmuted media. The panic cover video and preview clips rely
  on `muted` + `playsinline` (already set on several elements) — audit the rest. `playsinline` is
  present on the main `<video>` tags; keep it everywhere.
- **`crypto.randomUUID`** needs iOS 15.4+; **`navigator.mediaSession`** 15+;
  **`setSinkId`** only 18.4+ (audio output routing); **`VideoEncoder`** 16.4+ and
  **`AudioEncoder`** 26+ — so any in-browser transcoding (Mediabunny re-encode) is limited on older
  iOS. Gate those features by capability check and hide the UI when absent.
- **`MediaSource`** on iPhone was historically exposed only on iPad (`safari_ios` 13, partial,
  "iPad but not iPhone"). The app does not appear to use MSE today (no `MediaSource` in `ui/*.js`),
  which is good — keep it that way and stream via the loopback server instead.
- **`window.confirm` inside `vaultUnlock`** (the password screen) works, but the lock screen itself
  (`ul-lock`) is custom HTML and portable.
- **`fetch` with `Range`** on the media URL works over loopback HTTP (as it does today over
  `vault://`).
- **Viewport / safe areas.** The page sets `width=device-width` already; add
  `viewport-fit=cover` and `env(safe-area-inset-*)` padding so nothing sits under the notch/home bar.

## 8. Storage and privacy model on iOS

The Windows app's identity is "one tiny portable .exe, your files on your disk, nothing else on the
PC". iOS changes that contract:

- **No portable app.** The app lives in its sandbox; the vault lives in `Documents` (visible in the
  Files app if `UIFileSharingEnabled`/`LSSupportsOpeningDocumentsInPlace` are set) or in
  `Application Support` (hidden).
- **Untraceable mode** (encrypted hidden `data.temp`) still works — the encryption is pure Rust
  (`crypt.rs`: ChaCha20 + PBKDF2) — but "hidden from Explorer" becomes "hidden inside the sandbox",
  and "scrub the PC" has no iOS meaning beyond clearing the app's own caches. Keep the crypto, drop
  the Windows-specific hiding/scrubbing.
- **Cloud sync.** On Windows, "point the vault at a Drive/OneDrive/Dropbox/iCloud folder" is the
  primary sync story. On iOS there is no such folder to point at. Choose: (a) Drive API sync only
  (works today via `gdrive.rs`), or (b) iCloud Drive via a file-provider/document-based approach
  (significant extra work). Recommend (a) for the first version.
- **Backups / health checks / Excel / share packs** all work; route the output through the iOS share
  sheet (`UIActivityViewController`) instead of "open in Explorer".

## 9. Feasibility verdict and risks

**Feasible, as a sideloaded IPA, with meaningful work.** The page and most of the Rust backend are
portable; the iOS-specific work is bounded and each piece has a known approach.

Ranked risks:

1. **Media over custom scheme (high).** Mitigated by serving media over loopback HTTP. This is the
   single most important architectural decision and should be prototyped first.
2. **Origin mismatch (low effort, high impact).** One computed base URL instead of hardcoded
   `http://vault.localhost/`.
3. **CSP header size (medium, uncertain).** Measure on a device/simulator; fall back to an explicit
   CSP with hash injection disabled.
4. **Crate restructuring + macOS toolchain (medium, well-trodden).** `lib.rs` + `crate-type` +
   XcodeGen; needs a Mac or macOS CI.
5. **Windows-only backend paths (medium).** `trash` has no iOS backend; `explorer`, global shortcut,
   single-instance and self-update must be gated or replaced.
6. **Storage/cloud model (medium, product decision).** iOS cannot replicate "portable folder"; pick
   the Drive-API-only sync story.
7. **Touch/fullscreen/autoplay UX (medium).** No element fullscreen, no right-click, autoplay rules.
8. **Signing/sideloading (low, but account-dependent).** AltStore/TrollStore/paid account; free
   accounts need periodic re-signing.

Things that are **not** blockers (verified): `ureq`/`rustls`/`ring`/`getrandom`/`chacha20`/`image`
all build for iOS; `tauri-plugin-dialog` and `tauri-plugin-opener` support iOS; Tauri's iOS build
produces an IPA; the app already has a loopback HTTP server with the right range semantics to copy.

## 10. Suggested phased plan

Phase 1 is written up in full in `docs/IOS-PHASE-1.md` (foundation + format compatibility + Liquid
Glass). The phases below are the whole arc; Phase 1's detail lives in that file.

Each phase should end with a runnable build on a device or the simulator before the next starts.

**Phase 0 — prove the two scary things (a spike, throwaway code).**
- Restructure the crate (`lib.rs` + `crate-type` + thin `main.rs`).
- `tauri ios init` + `tauri ios dev` on a Mac; get the page to load in the iOS webview.
- Serve **one video** over a loopback HTTP server with range support and play it in a `<video>`.
  This is the go/no-go for the whole port.
- Build once and measure the CSP header size.

**Phase 1 — the media and origin layer.**
- Compute the base URL per platform; replace the hardcoded `http://vault.localhost/`.
- Move all media (images, video, audio) to the loopback server with the `fastlane` key pattern and
  an `Origin` check.
- Keep the page and IPC on the Tauri scheme.
- Fix the CSP if the header is over the limit.

**Phase 2 — the backend platform layer.**
- Gate `tauri-plugin-single-instance`, the global shortcut, self-update and `openDataFolder` behind
  `#[cfg(desktop)]`.
- Replace `explorer` with the iOS opener; replace `trash` with the in-vault trash on iOS.
- Move caches/sources/sign-in to the iOS sandbox paths.
- Wire `tauri-plugin-dialog` for pickers and the share sheet for exports.

**Phase 3 — storage and sync.**
- Default the vault to `Documents`; document-picker "open folder".
- Decide and implement the sync story (recommend Drive API only).
- Keep Untraceable's crypto; drop Windows hiding/scrubbing.

**Phase 4 — the UX pass.**
- Touch targets, long-press instead of right-click, no element fullscreen (CSS or
  `webkitEnterFullscreen`), in-page modals instead of `confirm`/`prompt`, safe-area insets.
- Capability-gate `VideoEncoder`/`AudioEncoder`/`setSinkId`.
- In-app emergency control to replace the global hotkey.

**Phase 5 — build and sign.**
- `tauri.conf.json` `bundle.iOS` (team, minimum version, frameworks, Info.plist with ATS local
  networking).
- `tauri icon` to generate the iOS asset catalog.
- GitHub Actions `macos-latest` job: `tauri ios build` → signed IPA (Apple API key) or `--no-sign`
  unsigned IPA; attach `LewdVault.ipa` to the release.
- Document the AltStore / TrollStore / paid-account install steps in the README.

## 11. Open questions for the user

1. **Sync on iOS:** Drive API only, or invest in iCloud Drive? (Recommend Drive API first.)
2. **Minimum iOS version:** 15.0 (Tauri default, wide reach) or higher? Note that **Liquid Glass
   only exists on iOS 26**, so on older iOS the app would show the `backdrop-filter` approximation
   instead. Recommend a low minimum (15/16.4) with glass as progressive enhancement, so the app runs
   on more devices and looks its best on 26.
3. **Vault visibility:** should the vault folder show in the Files app (`UIFileSharingEnabled`), or
   stay hidden in the sandbox? (Recommend visible for the normal vault, hidden for untraceable.)
4. **Emergency key:** in-app button/gesture, or attempt a system-level shortcut? (No global hotkeys
   on iOS.)
5. **A Mac available?** The iOS build cannot run on Windows; confirm a Mac or macOS CI runner is
   acceptable.
6. **Glass scope:** how far to push it — surfaces only (bars, sheets, controls), or also the layout
   (bottom tab bar, scroll edge effect, press-morph)? (Recommend both; they are what makes it read
   as native.)
