# Lewd Vault on iOS: research and feasibility

This is the research behind an iOS port. It answers what is possible, what breaks, and what a
build-and-sign pipeline looks like. It does not contain code changes yet. It is written to be read
next to `docs/GUIDE.md` (what the app does today) and `docs/PLAN.md` (how earlier rounds were run).

The goal, as asked: a **sideloaded IPA**, not an App Store release. Build it, sign it, install it
on a device the user controls (AltStore / SideStore / TrollStore / a free or paid Apple developer
account).

The short version: **the port is feasible, but it is a real port, not a rebuild of the same
binary.** Tauri 2 has a working iOS target, and the shared page in `ui/` already runs in a WebKit
webview. The hard parts are (1) how media is served (a custom scheme behaves differently on iOS),
(2) the Windows-only paths in the Rust backend (`explorer`, `trash`, `%LOCALAPPDATA%`, the global
shortcut), and (3) the build/sign toolchain, which needs macOS plus a small restructuring of the
Rust crate. None of those are blockers; each has a known fix.

**Two things outrank the rest, per the user's priorities:**

1. **Format compatibility.** The iOS app must read and write the *same vault folder* as the Windows
   app — same `index.csv`/`views.csv`, `_app/` layout, file names, ids and encryption — so a folder
   round-trips between the two with no loss. That contract is spelled out in
   `docs/IOS-PHASE-1.md`; every later decision has to respect it.
2. **Liquid Glass.** The iOS app should look native, not like a Windows app in a phone frame.
   Liquid Glass (iOS 26) has no free adoption in a webview, but WebKit exposes the real system
   material as `-apple-visual-effect: -apple-system-glass-material` (gated on
   `HAVE_MATERIAL_HOSTING`, which is defined for `PLATFORM(IOS)`), with `backdrop-filter` as the
   portable fallback. Details and the design tokens are in `docs/IOS-PHASE-1.md`.

## 2. Tauri 2 on iOS: what the toolchain gives you

Tauri 2 supports iOS (`tauri ios init|dev|build|run`). The moving parts:

- **Webview**: WKWebView, via `wry`. Custom protocols are registered as `WKURLSchemeHandler`s
  (`wry/src/wkwebview/mod.rs` calls `config.setURLSchemeHandler_forURLScheme`).
- **Minimum iOS version**: `bundle.iOS.minimumSystemVersion` in `tauri.conf.json`. Tauri's default
  is 15.0; this app sets **26.0**, because the target is iOS 26 and the UI leans on iOS 26 web
  features (Liquid Glass, `prefers-reduced-transparency`). The JS features the app uses need 15.4+
  (`crypto.randomUUID`) and some need far newer (section 3).
- **Xcode project**: generated by **XcodeGen** from a `project.yml` template
  (`crates/tauri-cli/templates/mobile/ios/project.yml`). You can supply your own template with
  `bundle.iOS.template`, and extra frameworks with `bundle.iOS.frameworks`.
- **Info.plist**: Tauri looks for `Info.plist` / `Info.ios.plist` next to `tauri.conf.json`, and
  `bundle.iOS.infoPlist` can point at a file to merge. This is where ATS and background settings go.
- **Build host**: iOS builds **require macOS + Xcode**. `tauri ios init` shells out to XcodeGen and
  Xcode's build tools; it does not run on Windows or Linux. That means a macOS CI runner (GitHub
  Actions `macos-latest`) or a Mac.
- **IPA output**: `tauri ios build` archives and exports an IPA. Flags that matter here:
  `--no-sign` (skip signing, produce an unsigned archive/IPA), `--archive-only`, and
  `--export-method` = `app-store-connect | release-testing | debugging`. `create_ipa()` zips
  `Payload/` with deflate.
- **Signing**: either an Apple API key (`APPLE_API_KEY`, `APPLE_API_KEY_PATH`,
  `APPLE_API_ISSUER`) or a `DEVELOPMENT_TEAM` in config, with `allow_provisioning_updates`.

**Conclusion:** the iOS target is a supported, first-class path. The work is in the app, not the
build system.

## 3. The origin and media problem (the biggest one)

### 3.1 The origin (fixed in Phase 1)

Tauri serves custom protocols from a different origin per platform
(`crates/tauri/src/protocol/mod.rs`):

```rust
if cfg!(windows) || cfg!(target_os = "android") {
    format!("{http}://{scheme}.localhost")   // http://vault.localhost
} else {
    format!("{scheme}://localhost")          // vault://localhost   (iOS/macOS/Linux)
}
```

The frontend originally hardcoded the Windows form (`const vaultUrl = id => 'http://vault.localhost/' + id`).
**That is already fixed:** the origin is now computed once by the backend (`vault_origin()` in
`lib.rs` — `media::origin()` on iOS, the Tauri scheme elsewhere) and handed to the page through the
`window.__VAULT_ORIGIN` initialization script. The page reads it back in one place:

```js
const vaultOrigin = () => (window.__VAULT_ORIGIN || 'http://vault.localhost').replace(/\/$/, '');
const vaultUrl = id => vaultOrigin() + '/' + encodeURIComponent(id);
```

So `getThumb`, the item list, `localFetch` and every `<video>`/`<audio>`/`<img>` source all go
through the one computed value. A test (`lib.rs`, `every_page_url_uses_the_computed_origin`, around
`lib.rs:2414`) guards that no call site reintroduces the literal. **Nothing left to do here** — this
was the single largest correctness risk on iOS and it is closed.

### 3.2 Why the custom scheme is the wrong tool for media on iOS

This is the part that decides the architecture. On iOS, WebKit routes `<video>`/`<audio>` through
AVFoundation, which is picky about custom URL schemes:

- **WebKit bug 146351** (`[GStreamer] Audio/video sources do not load via custom URI scheme`) — the
  media loader never reaches a custom scheme handler; the file simply does not play.
- **WebKit bug 324711 / PR 74641** (`[iOS] Custom URL scheme timeouts lead to crashes in
  mediaplaybackd`, reported 2026-09, fixed in WebKit 322083) — WebKit sets
  `AVAssetResourceLoadingContentInformationRequest.isEntireLengthAvailableOnDemand` for custom
  schemes, and expects requests to be answered *immediately*. A request that behaves like a network
  load and times out used to **crash `mediaplaybackd`**; the fix changes that to a load *error*
  instead of a crash. Apple's own note in the patch says some clients "re-implement HTTP loading via
  a custom URL scheme" — and that is exactly what this app's `vault://` does (byte ranges, `206`,
  `Content-Range`). So even on a fixed WebKit, custom-scheme media that looks like a network load is
  a fragile fit, and on devices running older iOS it can crash the media daemon outright.
- A well-known related limit: a custom scheme that answers range requests with a spec-correct
  `200`/`206` and `Content-Length` can still be rejected because AVFoundation insists on the
  "entire length available on demand" contract.

In practice: **images are usually fine over a custom scheme; video and audio are the problem.** The
app is video- and audio-heavy (Library preview clips, the player, Videos, Audio, the coach's clips,
the emergency cover video). So the custom scheme is a risk for a large part of the experience.

### 3.3 The recommended architecture: serve media over loopback HTTP

The app already contains a working loopback HTTP server with the exact semantics media wants. On
iOS, `media.rs` (already written) binds `127.0.0.1:0`, picks a free port, and forwards every request
to the same `serve()` (now in `lib.rs`) that answers `206` with `Content-Range` and a 4 MB
`RANGE_PIECE`; `fastlane.rs` is the desktop upload server built on the same pattern. On iOS, put the
media behind a **loopback HTTP server** (`http://127.0.0.1:<port>/…`) instead of a custom scheme:

- AVFoundation and WebKit treat `http://127.0.0.1` as ordinary HTTP: range requests, seeking and
  streaming all behave normally.
- The page keeps using `fetch`, `<img>`, `<video>` and `<audio>` unchanged — only the base URL
  differs.
- Security: bind to `127.0.0.1` only and require a per-launch random key on every request (the same
  pattern `fastlane.rs` already uses with `x-key`). Other apps on the device cannot reach
  `127.0.0.1` of another app's sandbox, and nothing off-device can. **Note:** the actual guard is the
  URL token, not an `Origin` check — `serve()` returns `Access-Control-Allow-Origin: *` and does not
  inspect `Origin` (the token is the first path segment; a wrong token is a `403`). That is fine for
  loopback, but do not describe it as an `Origin` check (an earlier draft did).
- ATS: loopback HTTP to `127.0.0.1` is not blocked by App Transport Security in practice, but the
  safe, explicit move is to add an ATS exception in `Info.plist`
  (`NSAppTransportSecurity` → `NSAllowsLocalNetworking` = true, and/or an `NSExceptionDomains`
  entry for `127.0.0.1` with `NSExceptionAllowsInsecureHTTPLoads`). Confirm on a real device.

There is a ready-made helper for the "serve the app's own assets over localhost" idea:
**`tauri-plugin-localhost`** (iOS supported, per its README). It serves bundled assets on a
localhost port and is worth reading, but it is aimed at the *app's static assets*, not the vault's
media, and it is flagged as carrying real security risk (no auth). For the vault's own media, a
purpose-built loopback server with the `fastlane` key pattern is a better fit. Whichever is chosen,
the media origin must be a plain `http://127.0.0.1:<port>`.

**One-origin alternative:** keep the *page* on the Tauri custom scheme (`tauri://localhost` on iOS;
`http://tauri.localhost` on Windows) and only put *media* on loopback HTTP. That keeps the IPC bridge
and the app's own scripts where Tauri expects them, and confines the HTTP server to byte-range media.
This is the recommended split.

### 3.4 CSP header-size risk

Tauri computes SHA-256 hashes of every bundled script and injects them into the CSP
(`crates/tauri/src/manager/mod.rs`, `set_csp` / `CspHash::Script`). WebKit enforces a **16 KiB limit
on HTTP header size**. With many separate `<script src>` tags (this app injects 18 of them from
`sync-ui.mjs`) the CSP header can grow large. Mitigations, in order of preference:

1. Set an explicit CSP in `tauri.conf.json` that allows the app's own scripts with `'self'` and
   disables the automatic hash injection via
   `app.security.dangerousDisableAssetCspModification` (the schema documents this). This trades a
   little automatic hardening for a small, fixed header.
2. Bundle the many small scripts into one or two files so fewer hashes are needed.
3. Keep `csp: null` (today's setting) and rely on the fact that the page is served from the app's
   own scheme. Verify the header actually stays under 16 KiB.

This is a "measure it" item: build once and inspect the response header. It is a known Tauri-on-iOS
report, not a certainty.

**Measured (13 Nov 2026).** The hash injection only happens when a CSP is configured at all: with
`csp: null`, `AppManager::csp()` returns `None` and `set_csp` is never called, so **no CSP header is
emitted** and the 16 KiB limit cannot be hit. Were a CSP added later, Tauri hashes **every** `.js`
asset it embeds, not just inline blocks (`tauri-codegen` `embedded_assets.rs`: `add_if_applicable`
SHA-256s each `.js`/`.mjs`, and `set_csp` folds those `CspHash::Script` values into `script-src`).
The built page (`src/index.html`) has 3 non-empty inline script blocks (**~160 bytes** of hashes —
three 53-byte `'sha256-…'` tokens plus separators) and 1 inline style block, and `src/` holds **20
`.js`/`.mjs` files** (18 page scripts plus `vendor/thumbhash.js` and `vendor/mediabunny.min.mjs`) —
so a CSP would carry 20 more 53-byte hashes, roughly **1.2 KB** in `script-src` total, still an
order of magnitude under WebKit's 16 KiB header limit. So **keep `csp: null` for Phase 1** (an explicit CSP would not remove these hashes
unless `dangerousDisableAssetCspModification` is set). Re-measure the actual response header on a
build if the script count grows a lot.

## 4a. Feature-parity matrix (the "replicate most features" answer)

The port's first priority is **compatibility with the Windows app and replicating most of its
features**. This table is the honest, feature-by-feature answer, grounded in the code (each row
names the module/command that implements it). Status values:

- **keeps** — the same code works on iOS unchanged.
- **works** — works on iOS after a small platform branch (already done in Phase 1, or trivially done).
- **adapt** — works, but the iOS UX must change (no window frame, no right-click, no Explorer).
- **replace** — a Windows-only mechanism with a different iOS mechanism (same feature, new plumbing).
- **defer** — kept in the code but not reachable/meaningful on iOS; out of scope for the first IPA.

The frontend is shared verbatim (`sync-ui.mjs` emits one `index.html`; `ui/*.js` are copied), so
every page feature is "keeps" unless the *platform* under it changes.

(Phase 4), and build/sign (Phase 5). Nothing in the format layer has to change — which is the
whole point.

## 6. Sideloading: how the IPA gets onto a device

Because this is explicitly **not** an App Store release, and the content is NSFW (App Store review
would reject it outright), the install paths are:

| Method | Needs | Notes |
| --- | --- | --- |
| **AltStore / SideStore** | A computer (AltServer) or a one-time local pairing; free or paid Apple ID | Signs the IPA with the user's own certificate, re-signs every 7 days on a free account. AltStore Classic runs AltServer on Windows/macOS (the user's Windows box is enough — no Mac needed); SideStore pairs once then is untethered (a local-VPN tunnel via its `em_proxy`/Jitterbug loopback method). Requires **iOS 14+**, so it covers iOS 26. The practical free path. |
| **TrollStore** | — | **Not an option on iOS 26.** Its supported range is 14.0–16.6.1, 16.7 RC and 17.0 only, and its README states 16.7.x (non-RC) and 17.0.1+ "will NEVER be supported". Kept here only for completeness. |
| **Free Apple ID + Xcode / `ios-deploy`** | A Mac + cable | 7-day provisioning profile, 3 apps max. Good for development. |
| **Paid Apple Developer ($99/yr)** | A Mac or CI | Ad-hoc / development signing with a 1-year profile, up to 100 devices. Cleanest for a personal build; CI can produce a signed IPA directly. |

For the *unsigned* artifact, `tauri ios build --no-sign` produces an IPA that a signer (AltStore,
SideStore, or `codesign`/`ldid` in CI) then signs. For a *signed* IPA, use an Apple API key in CI
with `--export-method debugging` (development) or `release-testing` (ad-hoc). (Verified against the
Tauri CLI source: `tauri ios build` accepts `--no-sign`, `--export-method
{debugging,release-testing,app-store-connect}` and `--archive-only`.)

**Recommended pipeline (built):** [`.github/workflows/ios.yml`](../.github/workflows/ios.yml) runs on a
`macos-26` runner (Xcode 26.6 + the iOS 26 SDK that `minimumSystemVersion: 26.0` needs). It installs
XcodeGen, runs `tauri ios init --ci`, writes the icon, then `tauri ios build`. With no Apple secrets
it runs `--no-sign` and uploads an **unsigned IPA** the user signs locally (AltStore/SideStore, or
`codesign`/`ldid`). With the `APPLE_API_KEY`, `APPLE_API_ISSUER` and `APPLE_API_KEY_P8` secrets set it
runs `--export-method debugging` and uploads a **signed IPA** ready for ad-hoc install. Artifact:
`LewdVault-ipa` (`src-tauri/gen/apple/build/<arch>/Lewd Vault.ipa`).

Caveat: a **free** Apple ID cannot be automated in CI the same way; AltStore's re-signing is the
practical free path. A paid account is the low-friction path.

## 7. Frontend: touch, keyboard, and web-platform gaps

The page was written for a desktop mouse/keyboard and a Windows webview. On iOS:

### 7.0 The audit (measured on the code, 13 Nov 2026)

Every count below is a `grep` over `ui/*.js` and the built `src/index.html`:

| Pattern | Count | iOS verdict |
| --- | --- | --- |
| `contextmenu` handlers | 3 (`library.js:427`, `privacy.js:136/159`) | Works (iOS fires `contextmenu` on long-press) but a long-press already means "hold to enlarge" in the grid, so the grid's right-click menu needs a different trigger on iOS. |
| `confirm` / `prompt` / `alert` | **24** (16 in `ui/*.js`: `audio.js`, `desktop.js`, `discover.js`, `drivesync.js`, `extras.js`, `library.js`, `privacy.js`, `videos.js`; 8 more in `src/index.html`) | **Silently dropped on iOS.** wry's iOS `WKUIDelegate` implements none of `runJavaScriptAlert`/`Confirm`/`TextInput`, and WebKit's `UIDelegate::UIClient` falls back to "no dialog": `alert` is a no-op, `confirm` returns `false`, `prompt` returns `""`/`null`. So a delete/reset that asks first **runs without asking**, and a rename/name prompt can never collect input. This is a correctness fix, not a polish item: replace with in-page modals (Phase 4). |
| `dblclick` | 3 (`library.js:982`, `look.js:304`, `player.js:206`) | Double-tap fires `dblclick` in WebKit, but it competes with double-tap-zoom; keep and verify. |
| `mousedown` / `mousemove` / `mouseup` | 8 (`desktop.js` ×6, `discover.js` ×1, `src/index.html:3695` ×1) | Mouse events still fire for touch in WebKit, but the tag/collection pickers should use `pointerdown` (the grid already does). |
| `pointerdown`/`pointermove`/`pointerup` | the grid, menus, resize grips (`library.js`) | The modern, correct set; works on iOS. This is the pattern to spread. |
| `requestFullscreen` | 1 (`src/index.html:576`), shadowed at runtime | `ui/slideshow.js` overwrites `showFullscreen` with the backend `window_action` version, so the element call never runs in practice. It survives only as a fallback and is a **no-op on iPhone** (MDN: `Element.requestFullscreen` is "only available on iPad, not on iPhone"), so it is harmless but dead; delete it or route it to `video.webkitEnterFullscreen()` (Phase 4). |
| `tauriInvoke('window_action', …'fullscreen')` | 3 call sites (`player.js:199` full, `:276` unfull, `slideshow.js:50` toggle) | Backend `window_action` on mobile now returns the toggle state, so the CSS full-bleed classes work (see below). |
| `touchstart`/`touchmove`/`touchend` | 0 (the grid uses pointer events) | n/a |

Conclusion: the page is already **pointer-event based** where it matters (the Library grid, menus,
the resize grips), which is the iOS-friendly path. The real gaps are the **right-click menus**
(contextmenu) and the **24 blocking dialogs**, both Phase 4 work, plus the fullscreen path (below).

- **Touch vs. mouse.** The grid, menus and drag handles use `pointerdown`/`pointermove`/`pointerup`
  (good). The remaining mouse-only handlers are the tag/collection pickers in `desktop.js` and
  `discover.js`; switch them to pointer events in Phase 4. The hold-to-enlarge affordance already
  works with a finger (pointer events).
- **Fullscreen.** `Element.requestFullscreen` appears once (`src/index.html:576`), but `ui/slideshow.js`
  overwrites `showFullscreen` at runtime with a version that calls the backend `window_action`, so the
  element API is effectively dead code and, on iPhone, would be a no-op anyway. The player's and
  slideshow's "full screen" both call the backend `window_action`; on the desktop that full-screens
  the OS window, and on iOS the mobile branch toggles a flag the page turns into the
  `html.vp-fullscreen` / `html.show-full` CSS full-bleed classes (there is no OS window to
  full-screen on iOS). For a video that should go truly full screen, `video.webkitEnterFullscreen()`
  remains available as a Phase 4 nicety.
- **Dialogs.** 24 `confirm`/`prompt`/`alert` calls (16 in `ui/*.js`, 8 in `src/index.html`). These
  are **not merely off-theme on iOS: they are silently dropped.** wry's iOS `WKUIDelegate` does not
  implement the JS-dialog methods, and WebKit's `UIDelegate::UIClient` treats a missing handler as
  "answer nothing" — `alert` does nothing, `confirm` returns `false`, `prompt` returns `""`/`null`.
  So on iOS the delete/reset/rename flows that gate on `confirm` would run **without confirmation**,
  and the rename/collection-name/bookmark prompts could never collect input. Replace all 24 with the
  app's own in-page modal (it already has `toast` and the modal plumbing) — Phase 4, and a
  correctness fix rather than a polish one.
- **Keyboard shortcuts.** The player and Library use keyboard handlers; they are harmless on iOS but
  the app needs on-screen equivalents (the player already has controls).
- **Autoplay.** The desktop sets `--autoplay-policy=no-user-gesture-required` (a WebView2 flag) so the
  emergency-key cover video starts *with sound*. That flag is WebView2-only; on iOS it is dropped.
  Wry's default `autoplay: true` does map to `setMediaTypesRequiringUserActionForPlayback(None)` on
  iOS, so the *gesture* requirement is lifted — but Safari's other gate (the "Never Auto-Play" /
  "Auto-Play" setting, and Low Power Mode) can still block unmuted autoplay, and
  `allowsInlineMediaPlayback` is forced on. So treat unmuted autoplay as best-effort on iOS: keep the
  emergency video `muted` + `playsinline` + a `play().catch(...)` that retries muted (the pattern
  `ui/privacy.js:142-144` already uses) so it never depends on a flag iOS ignores. `playsinline` is
  present on the main `<video>` tags; keep it everywhere.
- **`crypto.randomUUID`** needs iOS 15.4+; **`navigator.mediaSession`** 15+;
  **`setSinkId`** only 18.4+ (audio output routing); **`VideoEncoder`** 16.4+ and
  **`AudioEncoder`** 26+ — so any in-browser transcoding (Mediabunny re-encode) is limited on older
  iOS. Gate those features by capability check and hide the UI when absent.
- **`MediaSource` / streaming.** An earlier pass said the app does not use MSE; it does. `src/index.html`
  uses `window.ManagedMediaSource || window.MediaSource` (`index.html:1226` and `:2400`) for the
  on-demand "stream from Drive" player (`streamVideo`) and for the codec-copy decision
  (`chooseVideoCodec`). On iOS, plain `MediaSource` is "iPad but not iPhone", but
  **`ManagedMediaSource` is iOS 17.1+**, so on iOS 26 the code already prefers it and streaming works
  (the fragmented MP4 is pulled by `readRange` over the loopback server and appended). Keep the
  `MS.isTypeSupported` guard (it throws a clear error when a MIME is unsupported) and the
  `disableRemotePlayback` line Safari's `ManagedMediaSource` requires.
- **The lock screen (`vaultUnlock`)** is custom HTML (`ul-lock`, `src/index.html:537`) with its own
  password form — fully portable, and it contains no `confirm`/`prompt`. (An earlier note claiming a
  `window.confirm` there was wrong.)
- **`fetch` with `Range`** on the media URL works over loopback HTTP (as it does today over
  `vault://`).
- **Viewport / safe areas.** Done: the page sets `viewport-fit=cover` (both in `src/index.html:8` and
  injected by `sync-ui.mjs:314`) and `desktop.css` defines the four `env(safe-area-inset-*)` tokens
  (`--safe-t/r/b/l`, `desktop.css:2906`) used for the header and bottom bar, so nothing sits under
  the notch or the home indicator. Verify on a notched device (Phase 1.7 acceptance).

## 8. Storage and privacy model on iOS

The Windows app's identity is "one tiny portable .exe, your files on your disk, nothing else on the
PC". iOS changes that contract:

- **No portable app.** The app lives in its sandbox; the vault lives in `Documents` (visible in the
  Files app if `UIFileSharingEnabled`/`LSSupportsOpeningDocumentsInPlace` are set) or in
  `Application Support` (hidden).
- **Untraceable mode** (encrypted hidden `data.temp`) still works — the encryption is pure Rust
  (`crypt.rs`: ChaCha20 + PBKDF2) — but "hidden from Explorer" becomes "hidden inside the sandbox",
  and "scrub the PC" has no iOS meaning beyond clearing the app's own caches. Keep the crypto, drop
  the Windows-specific hiding/scrubbing.
- **Cloud sync.** On Windows, "point the vault at a Drive/OneDrive/Dropbox/iCloud folder" is the
  primary sync story. On iOS there is no arbitrary filesystem path to point at (the sandbox is
  fixed, and `pick_folder` is desktop-only), though an iCloud Drive folder *could* be reached
  through a document picker with security-scoped bookmarks. Choose: (a) Drive API sync only
  (works today via `gdrive.rs`), or (b) iCloud Drive via a file-provider/document-based approach
  (significant extra work). Recommend (a) for the first version.
- **Backups / health checks / Excel / share packs** all work; route the output through the iOS share
  sheet (`UIActivityViewController`) instead of "open in Explorer".

## 9. Feasibility verdict and risks

**Feasible, as a sideloaded IPA, with meaningful work.** The page and most of the Rust backend are
portable; the iOS-specific work is bounded and each piece has a known approach.

Ranked risks:

1. **Media over custom scheme (high).** Mitigated by serving media over loopback HTTP. This is the
   single most important architectural decision and should be prototyped first.
2. ~~**Origin mismatch (low effort, high impact).**~~ **Closed in Phase 1**: one computed base URL
   (`vault_origin()`) instead of a hardcoded `http://vault.localhost/`, pinned by a test.
3. **CSP header size (low, resolved by measurement).** With `csp: null` (today's setting) Tauri emits
   no CSP header at all, so the 16 KiB limit cannot be hit; if a CSP is ever added, the injected
   hashes are ~1.2 KB (see §3.4). No action needed for Phase 1.
4. ~~**Crate restructuring + macOS toolchain (medium, well-trodden).**~~ **Crate part done**
   (`lib.rs` + `crate-type` + thin `main.rs`). Still needs a Mac or macOS CI to run XcodeGen/`tauri
   ios`.
5. **Windows-only backend paths (medium).** Mostly done: `explorer`, `trash`, the global shortcut,
   single-instance and the storage paths are already `#[cfg(desktop)]`/iOS-branched. Done since:
   `maint.rs`'s `install_update` is `#[cfg(windows)]`-gated (no stray `app.exit(0)` on iOS), and the
   `fastlane.rs` Origin allowlist now includes the iOS page origin so iOS uploads are not `403`.
   Remaining: an in-app emergency control (Phase 4).
6. **Storage/cloud model (medium, product decision).** iOS cannot replicate "portable folder"; pick
   the Drive-API-only sync story.
7. **Touch/fullscreen/autoplay UX (medium).** No element fullscreen, no right-click, autoplay rules.
8. **Signing/sideloading (low, but account-dependent).** AltStore/TrollStore/paid account; free
   accounts need periodic re-signing.

Things that are **not** blockers (verified): `ureq`/`rustls`/`ring`/`getrandom`/`chacha20`/`image`
all build for iOS; `tauri-plugin-dialog` and `tauri-plugin-opener` support iOS; Tauri's iOS build
produces an IPA; the app already has a loopback HTTP server with the right range semantics to copy.

## 11. Open questions for the user

1. **Sync on iOS:** Drive API only, or invest in iCloud Drive? (Recommend Drive API first.)
2. **Minimum iOS version:** 15.0 (Tauri default, wide reach) or higher? Note that **Liquid Glass
   only exists on iOS 26**, so on older iOS the app would show the `backdrop-filter` approximation
   instead. Recommend a low minimum (15/16.4) with glass as progressive enhancement, so the app runs
   on more devices and looks its best on 26.
   **Decided: iOS 26.0** (`bundle.iOS.minimumSystemVersion`). The user's target is iOS 26, so the
   app can rely on the iOS 26 web features (Liquid Glass, `prefers-reduced-transparency`) without a
   fallback path for older versions; the `backdrop-filter` fallback stays as cheap insurance, not as
   a compatibility floor.
3. **Vault visibility:** should the vault folder show in the Files app (`UIFileSharingEnabled`), or
   stay hidden in the sandbox? (Recommend visible for the normal vault, hidden for untraceable.)
4. **Emergency key:** in-app button/gesture, or attempt a system-level shortcut? (No global hotkeys
   on iOS.)
5. **A Mac available?** The iOS build cannot run on Windows; confirm a Mac or macOS CI runner is
   acceptable.
6. **Glass scope:** how far to push it — surfaces only (bars, sheets, controls), or also the layout
   (bottom tab bar, scroll edge effect, press-morph)? (Recommend both; they are what makes it read
   as native.)
